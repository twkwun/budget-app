# 가계부 앱 제안 및 설계서

- 작성일: 2026-11-22
- 상태: 초안 (검토 후 확정 필요한 항목은 [9장](#9-확정이-필요한-사항)에 정리)

## 1. 요약

NAS에 직접 올려 쓰는 개인용 가계부 웹앱(PWA)을 만든다. 핵심 목표는 **카드 사용 내역 입력에 손이 거의 가지 않게 하는 것**이다.

결론부터 말하면, 개인이 카드사·은행 내역을 공식 API로 당겨오는 길은 사실상 막혀 있다. 그래서 다음 두 겹으로 수집한다.

1. **실시간 수집**: 카드 결제 알림 문자를 폰 자동화가 NAS로 그대로 전달하고, 서버가 파싱해서 자동 등록한다. 결제 직후 몇 초 안에 가계부에 들어온다.
2. **주기적 대조**: 한 달에 한 번 정도 뱅크샐러드(또는 카드사)의 엑셀 파일을 올리면, 빠진 건을 채우고 이미 들어온 건은 중복 없이 "확인됨"으로 표시한다.

사용자가 직접 하는 일은 "가끔 미분류 건을 한 번 탭해서 분류"와 "월 1회 파일 올리기" 정도로 줄어든다.

## 2. 내역 수집 방식 검토

### 2.1 공식 API는 왜 안 되는가

| 방식 | 개인 사용 | 이유 |
|---|---|---|
| 오픈뱅킹 (금융결제원) | 불가 | 이용기관으로 등록된 사업자만 사용 가능 |
| 마이데이터 | 불가 | 본인신용정보관리업 허가를 받은 사업자만 사용 가능 |
| 카드사 자체 오픈 API | 불가 | 제휴 사업자 대상 |
| CODEF (스크래핑 중개 API) | 제한적 | 아래 참조 |

**CODEF**는 카드사·은행 사이트를 대신 조회해 주는 API로, 카드 승인내역 조회 상품이 있다. 보도된 내용 기준으로 데모 버전은 3개월간 하루 100회까지 무료이고, 정식 버전은 사업자 정보 등록과 승인이 필요하다. 이 조건은 2021~2022년 기사에 근거한 것이라 가입 전에 현재 조건을 확인해야 한다. 개인이 장기간 쓸 수 있을지가 불확실하고 카드사 로그인 정보를 외부 서비스에 넘겨야 하므로, **핵심 경로로 삼지 않고 나중에 붙일 수 있는 선택 기능**으로 둔다.

### 2.2 대안 비교

| 방식 | 손이 가는 정도 | 실시간 | 비고 |
|---|---|---|---|
| A. 결제 문자 자동 전달 | 초기 설정 1회 | O | 권장. 폰 OS에 따라 방법이 다름 |
| B. 뱅크샐러드 엑셀 올리기 | 월 1회, 1분 | X | 권장. 모든 카드·계좌가 한 파일에 |
| C. 카드사별 엑셀 올리기 | 카드 수 × 월 1회 | X | B가 안 될 때의 대체 수단 |
| D. 캡처·영수증 사진 → AI 판독 | 건당 1회 공유 | △ | 선택. 현금·해외 결제 보완용 |
| E. 수동 입력 | 건당 10초 | O | 항상 제공 (현금 등) |
| F. CODEF 연동 | 초기 설정 1회 | △ | 선택. 조건 확인 후 결정 |

### 2.3 권장안: A + B 조합

**A. 결제 문자 자동 전달 (실시간)**

- **아이폰**: 단축어 앱의 "메시지를 받을 때" 자동화로, 카드사 발신 문자를 NAS의 웹훅 주소로 전송한다.
  - 아이폰은 다른 앱의 푸시 알림을 읽을 수 없어서 **문자(SMS)만** 대상이 된다. 지금 카드 알림을 앱 푸시로만 받고 있다면 카드사에서 문자 알림 서비스를 켜야 한다(카드사에 따라 월 300원 안팎의 이용료가 있을 수 있다).
  - "확인 없이 즉시 실행"이 메시지 자동화에서 동작하는지는 iOS 버전에 따라 다르다. **실기기에서 가장 먼저 검증할 항목**이다([7장](#7-개발-단계) 0단계).
- **안드로이드**: 알림 접근 권한을 가진 자동화 앱(MacroDroid, Tasker 등)으로 카드사 앱 푸시와 문자를 모두 잡아서 웹훅으로 보낸다. 문자 알림 서비스 가입이 필요 없다.

이 세션이 iOS 앱에서 시작된 것으로 보여 아이폰을 기본 가정으로 잡았다.

**B. 뱅크샐러드 엑셀 올리기 (월 1회 대조)**

뱅크샐러드는 마이데이터로 모든 카드·계좌 내역을 모아 두고, "데이터 내보내기 → 파일로 받기"로 최근 1년치를 비밀번호가 걸린 엑셀로 이메일 발송해 준다. 파일에는 "뱅샐현황"과 "가계부 내역" 두 시트가 있다. 이 파일 하나를 앱에 올리면 다음이 한 번에 해결된다.

- 문자 전달이 실패해서 빠진 건 보충
- 계좌 이체·자동이체처럼 문자가 오지 않는 내역 반영
- 앱을 쓰기 전 과거 1년치 내역 일괄 적재

메뉴 경로는 앱 버전에 따라 다를 수 있다.

**A만 쓰면** 폰이 꺼져 있거나 NAS에 접속이 안 될 때 누락이 생기고, **B만 쓰면** 실시간성이 없다. 둘을 합치면 각자의 약점이 가려진다.

## 3. 시스템 구성

```
[아이폰]                          [NAS - Docker Compose]
 결제 문자 ─ 단축어 자동화 ──┐      ┌────────────────────────────┐
 PWA (홈 화면 앱) ──────────┼─HTTPS─▶ 리버스 프록시               │
 엑셀 파일 올리기 ──────────┘      │    └▶ app 컨테이너            │
                                   │        ├ API 서버            │
[PC 브라우저] ─────────────────────▶        ├ 문자 파서·분류기     │
                                   │        ├ 웹 화면(정적 파일)   │
                                   │        └ SQLite (볼륨)       │
                                   │  백업: 매일 덤프 → 공유 폴더   │
                                   └────────────────────────────┘
```

### 3.1 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript (서버·화면 공통) | 파서와 타입을 양쪽에서 공유 |
| 서버 | Node.js LTS + Fastify | 가볍고 NAS 저사양에서도 충분 |
| DB | SQLite (WAL 모드) + Drizzle ORM | 아래 참조 |
| 화면 | Vue 3 + Vite + PWA | 홈 화면에 설치해 앱처럼 사용 |
| 차트 | ECharts | 도넛·추이 그래프 |
| 엑셀 | SheetJS + officecrypto-tool | 비밀번호 걸린 파일 해제 후 파싱 |
| 배포 | Docker 이미지 1개 + Compose | NAS에서 `docker compose up -d` |

**DB를 SQLite로 고른 이유**: 사용자가 한두 명이고 금액이 원 단위 정수라서 SQLite로 충분하다. 파일 하나라 백업·복구·이전이 쉽고, DB 컨테이너를 따로 띄우지 않아 NAS 메모리를 덜 쓴다. 다른 서비스에서 DB를 직접 조회하거나 NAS에 이미 PostgreSQL을 운영 중이라면 PostgreSQL로 바꾼다. ORM을 쓰므로 초기에 바꾸는 비용은 작다.

### 3.2 저장소 구조

```
budget-app/
├ apps/
│  ├ server/        API, 파서, 임포터, DB 마이그레이션
│  └ web/           Vue PWA

```

## 4. 데이터 설계

### 4.1 주요 테이블

| 테이블 | 역할 | 주요 필드 |
|---|---|---|
| `accounts` | 카드·계좌·현금 | 이름, 종류, 카드사, 끝 4자리, 결제일 |
| `transactions` | 거래 내역 | 일시, 금액(원, 정수), 유형, 가맹점, 분류, 수단, 메모, 상태, 출처, 할부 개월, 승인번호 |
| `raw_messages` | 수신 원문 보관 | 원문, 발신자, 수신 시각, 파싱 상태, 연결된 거래 |
| `categories` | 분류 (2단계) | 이름, 상위 분류, 지출/수입 구분 |
| `category_rules` | 자동 분류 규칙 | 가맹점 패턴, 분류, 우선순위, 생성 경로 |
| `import_batches` | 파일 가져오기 이력 | 파일명, 형식, 신규/중복/실패 건수 |
| `budgets` | 월 예산 | 연월, 분류, 금액 |
| `users` | 로그인 사용자 | 이름, 비밀번호 해시 |

- 거래 `유형`은 지출·수입·이체 세 가지다. **카드대금 출금, 내 계좌 간 이동은 이체**로 분류해 지출 합계에서 뺀다. 이걸 빼지 않으면 카드 사용액이 두 번 잡힌다.
- 거래 `상태`는 정상·취소·확인 필요 세 가지다.
- 원문을 `raw_messages`에 항상 남긴다. 파서를 고치면 과거 문자를 다시 돌릴 수 있다.

### 4.2 문자 파싱 흐름

```
수신 → 원문 저장 → 카드사 판별 → 카드사별 정규식 파서
     → 성공: 거래 생성 → 자동 분류 → 완료
     → 실패: "확인 필요"로 인박스에 표시 (원문과 함께)
```

- 추출 항목: 승인/취소 구분, 금액, 가맹점, 일시, 카드 끝자리, 일시불/할부
- 파서는 사용 중인 카드사부터 만든다. 카드사마다 문구가 달라서 **실제 문자 샘플**(이름·카드번호 가린 것)이 필요하다.
- 취소 문자는 같은 카드·금액·가맹점의 원 거래를 찾아 취소 처리한다.
- 정규식이 실패한 문자를 LLM으로 판독하는 기능은 선택 사항이다([9장](#9-확정이-필요한-사항)).

### 4.3 중복 제거

파일을 올릴 때 각 행을 기존 거래와 대조한다.

1. 승인번호가 있으면 승인번호로 대조
2. 없으면 `수단 + 금액 + 날짜(±1일)`로 후보를 찾고 가맹점명 유사도로 확정
3. 일치하면 새로 넣지 않고 기존 거래를 "확인됨"으로 표시
4. 애매한 건은 미리보기 화면에서 사용자가 고른다

날짜에 ±1일 여유를 두는 것은 승인일과 매입일이 다를 수 있어서다.

### 4.4 자동 분류

우선순위 순서대로 적용한다.

1. 사용자가 만든 가맹점 규칙 (정확히 일치)
2. 같은 가맹점의 직전 분류
3. 기본 키워드 규칙 (편의점, 주유소, 배달앱 등)
4. 해당 없으면 "미분류"로 인박스에 표시

분류를 고치면 "이 가맹점은 앞으로도 이렇게 분류"를 물어 규칙으로 저장한다. 쓸수록 미분류가 줄어든다.

네이버페이·카카오페이 같은 간편결제는 문자에 실제 가맹점이 나오지 않는 경우가 많다. 이런 건은 미분류로 남기고, 월 1회 파일 대조 때 상세 정보가 있으면 보충한다.

## 5. 화면 구성

| 화면 | 내용 |
|---|---|
| 홈 | 이번 달 지출·수입, 예산 대비 진행률, 분류별 도넛, 일별 추이, 미분류 건수 |
| 내역 | 월별 목록, 검색·필터(분류, 수단, 금액), 한 줄 탭으로 수정 |
| 인박스 | 미분류·확인 필요 건을 카드 형태로 넘기며 한 번 탭으로 처리 |
| 추가 | 금액 → 분류 → 저장 3단계 수동 입력 |
| 가져오기 | 파일 선택 → 미리보기(신규/중복/확인 필요) → 반영 |
| 통계 | 월별·연별 비교, 분류별 추이 |
| 설정 | 카드·계좌, 분류, 규칙, 예산, 웹훅 토큰, 백업 |

모바일 화면을 우선으로 만들고, PC에서는 넓은 표 형태로 보여 준다.

## 6. 배포와 보안

### 6.1 NAS 배포

- GitHub Actions가 이미지를 빌드해 GHCR에 올리고(amd64·arm64 둘 다), NAS에서는 받아서 실행만 한다. NAS에서 직접 빌드하지 않는다.
- 데이터는 NAS 공유 폴더에 볼륨으로 연결한다. 컨테이너를 지워도 데이터는 남는다.
- 매일 새벽 DB 덤프를 별도 폴더에 저장하고 최근 30일분을 유지한다. NAS의 기존 백업 작업에 이 폴더를 포함시킨다.

### 6.2 외부 접속

밖에서 결제한 문자가 NAS에 도달해야 하므로 외부 접속 경로가 필요하다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 리버스 프록시 + HTTPS (DDNS) | 폰에 추가 앱 불필요, 자동화가 안정적 | 인터넷에 노출됨 |
| Tailscale | 인터넷에 노출 안 됨 | 폰에서 VPN이 꺼져 있으면 전달 실패 |
| Cloudflare Tunnel | 포트 개방 불필요 | 외부 서비스 의존 |

이미 NAS를 밖에서 쓰는 방식이 있으면 그것을 따른다. 새로 정한다면 리버스 프록시 + HTTPS를 권장한다. 전달 실패 건은 어차피 월 1회 파일 대조로 메워진다.

### 6.3 보안

- 화면은 로그인 필수 (비밀번호 해시, 세션 쿠키)
- 웹훅은 기기별 긴 토큰으로 인증하고 요청 횟수를 제한한다. 토큰은 설정 화면에서 재발급할 수 있다.
- 카드번호는 끝 4자리만 저장한다.
- 비밀값은 `.env`로 주입하고 저장소에 올리지 않는다.
- **저장소가 공개 상태다.** 실제 문자 원문, 엑셀 파일, DB 파일은 절대 커밋하지 않는다. 테스트용 샘플은 이름·금액·가맹점을 바꾼 것만 쓴다. 코드를 공개할 이유가 없으면 비공개로 바꾸는 것을 권한다.

## 7. 개발 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0. 검증 | 단축어 문자 자동화가 확인 없이 도는지, 뱅크샐러드 파일 받기가 되는지 실기기 확인 | 테스트 문자가 임시 웹훅에 도착 |
| 1. 뼈대 | 저장소 구조, DB, 로그인, Docker 이미지, NAS 배포 | NAS에서 빈 앱이 뜸 |
| 2. 기본 가계부 | 수동 입력, 내역, 분류, 홈 화면 | 수동으로 한 달 써볼 수 있음 |
| 3. 문자 수집 | 웹훅, 카드사 파서, 자동 분류, 인박스 | 결제 후 자동 등록됨 |
| 4. 파일 가져오기 | 뱅크샐러드·카드사 엑셀, 중복 제거, 미리보기 | 과거 1년치 적재 |
| 5. 예산·통계 | 월 예산, 비교 통계, 고정지출 | |
| 6. 선택 기능 | CODEF 연동, AI 판독, 가족 공유 | 필요할 때 |

0단계를 먼저 하는 이유는, 결과에 따라 3단계의 설계가 달라지기 때문이다. 문자 자동화가 매번 확인을 요구한다면 실시간 수집을 포기하고 파일 가져오기(4단계)를 앞으로 당긴다.

## 8. 위험 요소

| 위험 | 대응 |
|---|---|
| iOS 업데이트로 단축어 자동화 동작이 바뀜 | 파일 대조가 항상 보조 수단으로 남아 있음 |
| 카드사가 문자 문구를 바꿈 | 원문을 보관하므로 파서 수정 후 재처리. 실패 건은 인박스에 보임 |
| 뱅크샐러드가 내보내기 기능이나 파일 형식을 바꿈 | 카드사별 엑셀 가져오기로 대체 |
| NAS 장애·디스크 손상 | 매일 덤프 + NAS 외부 백업 |

## 9. 확정이 필요한 사항

1. **폰**: 아이폰만 쓰는지, 안드로이드 기기도 있는지
2. **NAS**: 제조사·모델(시놀로지, QNAP 등), Docker 사용 가능 여부, 현재 외부 접속 방식
3. **카드사**: 쓰는 카드사 목록, 결제 알림을 문자로 받는지 앱 푸시로 받는지
4. **사용자**: 혼자 쓰는지, 가족과 같이 쓰는지
5. **범위**: 카드만 볼지, 계좌 입출금·현금까지 볼지
6. **뱅크샐러드**: 이미 쓰고 있는지, 새로 가입해서 쓸 의향이 있는지
7. **AI 판독**: 파싱 실패 문자나 영수증 사진을 외부 LLM API로 보내도 되는지 (결제 내역이 외부로 나감)
8. **저장소 공개 여부**: 공개 유지 또는 비공개 전환

이전에 만든 앱들의 구성(스택, 배포 방식)은 이 세션에서 확인할 수 없었다. 그 앱들과 같은 방식으로 맞추고 싶다면 알려 주면 3장과 6장을 그에 맞춰 고친다.
